# Pisper 前端样式与页面布局审计

> 基线说明：审计证据来自 2026-10-14 的 Rust 分支代码，并非恢复后的 `v0.5.81` Node 基线。代码引用固定到当时的提交；在 Node 分支治理样式前，需要重新验证问题是否存在及其位置。原完整代码保存在 `rust-runtime`。

- 日期：2026-10-14
- 状态：现状审计与治理建议，尚未修改产品实现。
- 关联方案：[前端工作台设计方案](2026-10-14-frontend-workbench-design.md)。
- 范围：样式来源、颜色语义、基础组件、页面布局、响应式与滚动职责。

当前问题不是 Tailwind 没有接入，而是迁移尚未形成统一的设计系统。新旧变量并存，部分工具类缺少主题映射，一些旧 CSS 被逐字搬成了任意值与父级选择器；页面虽共享应用壳，但容器、间距、滚动与列表详情结构仍各自实现。

建议沿用已经确认的中性工作台方向：中性底色与主操作、有限的交互强调色、独立的状态色；使用少量页面模板统一布局规则。治理顺序是先修复确定性缺陷，再整理令牌和组件，最后按页面类型迁移，不以清空 CSS 文件或提高 Tailwind 使用比例作为验收标准。

## 1 检查范围与方法

已核对 `package.json`、`components.json`、样式入口、应用壳、主题偏好与自定义强调色实现，以及聊天、配置、技能、MCP、插件、资源、工作流、渠道、计划任务、记忆和决策模型页面。

检查采用三种方式：

1. 搜索源码中的 CSS 文件、变量、页面容器、滚动与父级选择器。
2. 使用项目已安装的 `@tailwindcss/node` 编译实际 `src/index.css` 及其导入，检查指定工具类是否生成规则。这是隔离编译探针，不是整项目生产构建。
3. 在独立 Chromium 页面中载入实际主题 CSS，读取主操作前景与背景的计算色，并计算对比度；另外检查字号覆盖与自定义白色焦点。没有启动或操作真实用户会话。

本轮未执行全量类型检查、lint、产品构建、Runtime 测试或平台设备验收。未修改生产代码；浏览器探针的结果只覆盖下文列明的样式行为，不代表全部页面或平台已完成视觉验收。

## 2 样式现状

### 2.1 独立 CSS 的实际分布

`src/` 下当前只有两份 `.css` 文件：

| 文件                                       | 当前规模 | 主要内容                                                                                  |
| ------------------------------------------ | -------- | ----------------------------------------------------------------------------------------- |
| `src/index.css`                            | 898 行   | 主题变量、预设、Tailwind 映射、基础规则、动画、Markdown 与第三方控件适配、旧 WebView 降级 |
| `src/components/react-bits/react-bits.css` | 297 行   | 文本、卡片和装饰效果的局部样式及动画                                                      |

行数仅用于定位分布，不作为质量门槛。`index.css` 中大量内容属于主题定义、关键帧和第三方适配，不能一概视为应该删除的业务 CSS。

真正广泛的存量问题存在于 TSX：页面和共享组件同时使用语义工具类、旧 `var(--...)` 引用、任意像素值、任意 CSS 属性和依赖业务父级类名的变体。

例如计划任务详情区域还携带 `.memory-layout`、`.mcp-layout`、`.skills-layout` 等其他页面的匹配条件；在当前页面不一定生效，却使该段布局依赖不相关的页面结构。这说明部分迁移只是改变了样式的书写位置。

### 2.2 正常保留的 CSS

| 内容                                          | 建议                                         |
| --------------------------------------------- | -------------------------------------------- |
| 设计令牌、浅深主题、Tailwind `@theme` 映射    | 保留为设计系统的单一入口                     |
| 页面基础元素规则和重置                        | 保留，但检查是否压过组件自身契约             |
| 关键帧及无法清楚表达的复杂动画                | 保留，明确所属功能与减少动态效果行为         |
| Dockview、xterm、Streamdown 等生成 DOM 的适配 | 保留有范围的样式，并与第三方版本变化一起验证 |
| Safari 与旧 WebView 的必要降级                | 保留兼容性保护，不能为追求纯工具类直接删除   |
| 一次性页面布局、控件外观、重复卡片和列表组合  | 迁入对应组件、类型化变体和布局模板           |

Tailwind 官方同时支持主题变量、自定义样式和任意值。项目需要的是统一使用边界，而不是禁止所有 CSS。[主题变量](https://tailwindcss.com/docs/theme)、[自定义样式](https://tailwindcss.com/docs/adding-custom-styles)

## 3 已确认的实现问题

### S01 部分语义工具类没有生成样式

实际入口隔离编译结果：

| 工具类                    | 是否生成对应规则 |
| ------------------------- | ---------------- |
| `bg-surface-subtle`       | 否               |
| `bg-surface-hover`        | 否               |
| `text-brand`              | 否               |
| `bg-surface-muted`        | 是               |
| `bg-brand-soft`           | 是               |
| `text-brand-strong`       | 是               |
| `bg-primary`              | 是               |
| `text-primary-foreground` | 是               |

源码定义了 `--surface-subtle` 等普通 CSS 变量，但没有相应的 `--color-surface-subtle`、`--color-surface-hover` 和 `--color-brand` 映射。普通 CSS 变量存在，不等于 Tailwind 会生成同名工具类。

直接影响示例：

- `PageHeader.tsx` 中终端打开状态使用 `bg-surface-hover text-brand`，预期的这两项状态样式没有输出。
- `ChatMessage.tsx` 中已保存标签状态使用同样组合。
- 多处取消按钮、返回入口及对话框使用 `bg-surface-subtle`，预期底色无法由该类提供。

相关代码：[主题映射](https://github.com/ling-kong-ran/pisper/blob/2b1c97afb529d8dc8170ad0c905c71b921ef5788/src/index.css)、[页面标题栏](https://github.com/ling-kong-ran/pisper/blob/2b1c97afb529d8dc8170ad0c905c71b921ef5788/src/components/layout/PageHeader.tsx)、[消息组件](https://github.com/ling-kong-ran/pisper/blob/2b1c97afb529d8dc8170ad0c905c71b921ef5788/src/features/chat/components/message/ChatMessage.tsx)。

**处理建议：** 先确定需要保留的颜色角色，再补齐映射或替换为已有正确令牌。不能只凭类名可读就认定迁移完成；应以编译输出及实际状态样式为证据。

### S02 彩色预设的主按钮前景对比不足

主按钮使用 `bg-primary text-primary-foreground`；当前映射为 `--star` 和 `--on-accent`。暗色彩色预设提高了背景亮度，但仍统一使用白色前景。

按照实际 CSS 计算色测量默认实心状态：

| 强调方案 | 浅色前景对比度 | 暗色前景对比度 |
| -------- | -------------- | -------------- |
| neutral  | 17.72:1        | 13.41:1        |
| blue     | 4.34:1         | 2.48:1         |
| teal     | 5.47:1         | 2.02:1         |
| violet   | 5.31:1         | 2.65:1         |
| coral    | 4.41:1         | 2.42:1         |

这些是前景与实心背景之间的对比度，不包含 hover、disabled、透明叠加或所有页面背景。普通大小文字的 WCAG AA 基准为 4.5:1；四套暗色彩色预设，以及浅色 blue、coral 的这一组合低于该基准。[W3C 文字对比度说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

相关代码：[主题预设](https://github.com/ling-kong-ran/pisper/blob/2b1c97afb529d8dc8170ad0c905c71b921ef5788/src/index.css)、[Button](https://github.com/ling-kong-ran/pisper/blob/2b1c97afb529d8dc8170ad0c905c71b921ef5788/src/components/ui/button.tsx)。

**处理建议：** 默认主操作保留中性强对比。确需彩色实心控件时，前景必须随背景选择并校验，不能让暗色预设固定使用白字。验收覆盖默认、悬停、按下和禁用的实际组合。

### S03 自定义色的焦点轮廓没有独立对比保障

`customAccentStyleRules` 已经为强调色文字与实心背景选择前景，不能把现状概括为完全没有对比度处理。但焦点变量仍直接等于用户输入色。

隔离探针中，自定义 `#ffffff` 配浅色页面会得到白色焦点轮廓与白色背景，二者为 1:1。文字可以仍然可读，但该焦点标记本身不可辨识。

相关代码：[自定义强调色派生](https://github.com/ling-kong-ran/pisper/blob/2b1c97afb529d8dc8170ad0c905c71b921ef5788/src/lib/format/custom-accent.ts)、[偏好应用](https://github.com/ling-kong-ran/pisper/blob/2b1c97afb529d8dc8170ad0c905c71b921ef5788/src/app/ui-preferences.ts)。

**处理建议：** 将焦点颜色作为独立输出，在实际相邻表面上校验。必要时调整明度或提供双层轮廓，不用未经约束的原始 HEX 直接充当 `ring`。对于用于识别控件和状态的非文本视觉信息，参考 3:1 的相邻色对比要求；不把所有装饰性分隔线都机械纳入该要求。[W3C 非文本对比度说明](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

### S04 新旧令牌和颜色角色混用

当前样式中同时存在：

- `--star`、`--blue`、`--brand-blue` 等历史或视觉命名。
- `--primary`、`--accent`、`--ring` 等组件语义命名。
- `--text`、`--stroke`、`--r-*`、`--sh-*` 与较新的语义工具类。

其中 `--blue` 在默认方案里映射到中性主操作，`--brand-blue` 又会随 teal、violet、coral 预设改变颜色。名称已经不能可靠说明用途。

`StatusBadge` 的 `tone="blue"` 使用品牌色相关令牌，这意味着信息状态会随用户强调色改变。问题不是自定义颜色本身，而是品牌、交互和状态共用了部分角色。

相关代码：[主题变量](https://github.com/ling-kong-ran/pisper/blob/2b1c97afb529d8dc8170ad0c905c71b921ef5788/src/index.css)、[应用级 UI 组合](https://github.com/ling-kong-ran/pisper/blob/2b1c97afb529d8dc8170ad0c905c71b921ef5788/src/components/ui/app-primitives.tsx)。

**处理建议：** 建立语义角色后分批迁移。旧变量仅作为有明确删除条件的兼容映射，新组件直接使用语义工具类。

### S05 共享组件依赖页面结构

`AppSectionTitle` 包含 `.model-config-heading`、`.skill-scope-head` 等父级条件；`AppCard` 依赖 `.detail-stack`；`StatusBadge` 包含 `.cli-settings-heading` 条件。基础展示组件因此知道了业务页面中的特定类名。

页面内部也复制了其他领域的祖先选择器。计划任务、MCP、技能等详情容器中存在重复的跨页面布局规则。

这类依赖没有通过参数表达。移动组件或替换父容器时，样式可能悄悄改变，调用方也难以判断默认外观。

**处理建议：** 由页面提供布局，组件通过明确的 `size`、`density`、`tone`、`className` 或插槽接收必要变化；不要把 Feature 名称编码到基础组件的 CSS 选择器中。App 层组合放在合适的 `components/app` 或布局目录，领域规则仍留在 Feature。

### S06 字号缩放存在两套行为

全局 `small { font-size: var(--app-small-size) !important; }` 会覆盖组件设置的 `small` 字号。与此同时，大量固定 `text-[13px]` 不随界面字号设置缩放。

隔离探针中，相同的显式 13px：

| 元素               | small 字号偏好 | default 字号偏好 | large 字号偏好 |
| ------------------ | -------------- | ---------------- | -------------- |
| `small` 元素       | 11.57px        | 12px             | 12.43px        |
| 普通固定 13px 文本 | 13px           | 13px             | 13px           |

这说明字号变化取决于元素标签与写法，而不是单一排版角色。

**处理建议：** 使用界面正文、辅助信息、标题、对话阅读、代码等明确角色。移除覆盖所有 `small` 的重要性规则前，先将调用方迁移到对应角色；代码与终端字号继续保留其独立设置。

### S07 布局容器与滚动职责分散

应用壳已经为非聊天页面提供外边距与 `overflow-auto`，页面内部又分别添加外边距、全高和滚动容器。

| 页面             | 当前实现信号                                                   | 需要统一的方面                         |
| ---------------- | -------------------------------------------------------------- | -------------------------------------- |
| 决策模型         | 壳层外边距之外又有 `max-w-3xl p-6`，加载、错误与正常态容器不同 | 表单宽度、外边距所有者、状态布局稳定性 |
| 配置             | 只有模型区设置 `max-w-[1040px]`，其他区由内部组件决定          | 设置页面的宽度与分节规则               |
| 计划任务         | 310px 列表加详情，900px 切单列，并自行管理列表高度             | 列表详情模板、窄屏路径、滚动范围       |
| MCP              | 230px／内容／300px 三栏，1150px 与 650px 切换                  | 第三栏是否为检查器、局部可用宽度与滚动 |
| 技能             | 三列采用另一组比例和最小宽度                                   | 与同类管理页共享主结构，保留业务差异   |
| 插件             | 壳层滚动之外又有 `h-full overflow-y-auto`                      | 双层滚动风险与工具栏定位               |
| 资源与工作流列表 | 自己维护工具栏、卡片网格和高度                                 | 集合页模板、过滤与空态                 |
| 工作流编辑器     | 使用 `calc(100dvh - 220px)` 一类页面高度推算                   | 工作台实际容器尺寸与画布滚动边界       |

这些差异可由源码确认；其中具体溢出或双滚动在多少尺寸出现，还需要完整页面运行验证，不能仅凭静态样式断言所有页面已发生故障。

### S08 默认组件外观与新布局方向不一致

共享 `AppCard` 默认携带表面阴影、背景模糊和标题后代选择器；空态包含较大的装饰图标区域与多层视觉效果。原生 `Card`、`AppCard` 和页面自行设置的面板又有不同的间距与圆角。

这些不一定都是功能错误，但与已确认的轻量工作台方向不一致。应按普通分区、资源卡片、浮层三类表面定义默认外观，而不是所有区块都套用同一种带装饰效果的卡片。

## 4 Tailwind 与 CSS 的统一规则

### 4.1 建议的四层结构

| 层级           | 职责                                   | 使用方式                                 |
| -------------- | -------------------------------------- | ---------------------------------------- |
| 设计令牌       | 颜色、字号、间距尺度、圆角、阴影与主题 | CSS 变量及 `@theme` 映射                 |
| 基础控件       | Button、Input、Dialog、Tabs、Sheet 等  | 优先既有 shadcn，变化用类型化变体        |
| 应用布局与组合 | 页容器、页头、工具栏、列表详情、空态   | React 组件组合 Tailwind 工具类           |
| 领域界面       | 当前页面的数据、交互与业务展示         | 消费上述组件；领域模型与请求仍归 Feature |

### 4.2 具体约束

- 常规布局优先使用既有间距、字号和圆角尺度；确有特殊尺寸才使用任意值。
- 重复的工具类组合提取为有明确职责的组件或类型化变体，不转换成新的全局语义类。
- 动态坐标、拖拽宽度、图形位置和 CSS 自定义属性可以使用内联样式；不能把所有 `style` 都当作违规。
- 新代码不再引用已标记退役的 `--r-*`、`--sh-*` 等变量，也不复制其他 Feature 的父级类名选择器。
- `!important` 只用于已解释的第三方或兼容性边界。控件尺寸冲突优先通过组件契约解决。
- 不通过增加 `@apply` 别名把业务 CSS 藏进全局文件。
- 是否拆分主题与第三方适配文件，依据责任和导入顺序决定；拆文件本身不算治理完成。

验收应关注工具类是否真实生成、状态是否正确、组件是否仍依赖外部业务 DOM、主题切换与兼容性是否保持，而不是以代码行数或“纯 Tailwind 比例”评价质量。

## 5 强调色方案

### 5.1 三种方向

| 方向                          | 特点                                               | 取舍                                             |
| ----------------------------- | -------------------------------------------------- | ------------------------------------------------ |
| 中性主操作与有限交互强调 推荐 | 主按钮和大面积结构保持中性；少量交互使用可控强调色 | 最贴近已确认工作台，降低全页面着色噪声           |
| 全面品牌强调                  | 主按钮、选择项、徽标和部分面板都跟随用户色         | 个性更明显，但状态易混淆，对比度组合更多         |
| 全部单色                      | 交互也主要依赖灰阶、边界与文字                     | 简洁，但焦点、链接与活动状态需要更强的非颜色标识 |

推荐第一种。当前默认 neutral 已接近这个方向，不需要为改进强调色先换一个全新的品牌颜色；重点是限制作用范围并补齐可读性保障。

### 5.2 颜色角色

| 角色                           | 默认规则                             | 是否随用户强调色变化               |
| ------------------------------ | ------------------------------------ | ---------------------------------- |
| 背景、导航、面板               | 中性表面层级                         | 否                                 |
| 主操作 `primary`               | 浅色墨色，深色反白，保证前景对比     | 默认否                             |
| 常规 hover 与选择底色 `accent` | 轻量中性表面，遵守 shadcn 的组件语义 | 默认否                             |
| 活动指示、部分交互链接         | 少量强调色，避免大面积填充           | 可变化，但使用经过校验的派生色     |
| 键盘焦点 `ring`                | 与相邻表面可辨识                     | 可派生，不能直接等于任意原始输入色 |
| 信息、成功、警告、危险         | 独立语义颜色与文字标识               | 否                                 |
| 代码、Diff、图表与资源类型     | 内容自身语义                         | 不随界面强调色统一替换             |

`accent` 在组件系统中常用于轻量交互表面，不应简单等同于“用户选中的品牌色”。新角色通过语义名称表达，旧的 `blue`、`star` 命名留作短期兼容映射。

已有自定义强调色和预设不能静默丢弃。若接受收窄作用范围的方案，需要同时调整设置说明和迁移规则；本审计不直接改变用户偏好。

颜色校验矩阵至少包含浅深主题、各预设、自定义极亮／极暗颜色、默认与悬停、焦点、禁用、选中、错误，以及所在表面的实际背景。自定义强文字的现有对比度计算可以复用，不重复建立无约束的另一套算法。

## 6 页面布局统一方案

统一不是让所有页面拥有相同栏数，而是让同类页面共享容器、标题、工具栏、密度和滚动规则。

### 6.1 四种页面模板

| 模板     | 适用页面                                            | 布局规则                                                         |
| -------- | --------------------------------------------------- | ---------------------------------------------------------------- |
| 工作台   | 聊天任务、工作流编辑器、需要画布的界面              | 占满可用区域；工具、画布、对话各有明确滚动所有者                 |
| 列表详情 | 计划任务、渠道、MCP、技能管理、记忆管理中的列表视图 | 左列表右详情；可选检查器；窄屏转列表与详情单面切换               |
| 集合页   | 资源库、插件市场、工作流列表                        | 统一页头与过滤工具栏；内容区域使用列表或自适应卡片网格           |
| 设置表单 | 模型、外观、通知、远程访问、决策模型等              | 统一受限宽度、分节、标签与操作位置；复杂模型工作台允许明确的宽版 |

同一领域可以包含多种模板，例如工作流列表和工作流编辑器；不要按 Feature 名称强制全部页面套入同一种布局。

### 6.2 共同的页面契约

1. **外边距只有一个所有者。** 由页面容器控制，子页面不重复加整页 `p-6`。
2. **标题与操作分离。** 应用标题栏承担窗口与导航；业务页头承担当前页面名称、说明和主动作。
3. **工具栏位置一致。** 搜索、筛选、排序和视图切换在统一区域，窄屏按明确顺序换行或收入菜单。
4. **滚动所有者明确。** 文档／集合页由内容容器滚动；工作台由各面板滚动；避免壳层与页面全高容器同时争夺滚动。
5. **空态与正常态不换布局骨架。** 加载、错误、无数据保留标题、工具栏和相同宽度约束。
6. **主动作位置稳定。** 不因正在加载或是否选中一项而来回移动；没有目标时使用正确的禁用或隐藏语义。
7. **按可用空间适配。** 工作台与列表详情优先观察内容容器宽度；不能只凭窗口 650／900／1150px 推断面板是否放得下。
8. **表单与内容密度区分。** 默认控件尺寸沿用既有变体；紧凑列表与手机触摸尺寸通过显式密度约定实现。

可形成少量应用级组合：页面容器、页头、工具栏、分节标题、列表详情布局和状态视图。组件只接收展示数据、插槽与回调，不导入 Feature 业务实现。

### 6.3 初始视觉节奏

- 页面外边距以桌面 24px、手机 12–16px 为起点，统一由容器决定。
- 常规区块间距优先使用 16px，主要分节使用 24px；紧凑条目可以使用 8px 或 12px。
- 对话阅读宽度沿用前端方案约 780px 的目标；设置表单另设统一受限宽度，复杂编辑面板采用宽版，不混用任意最大宽度。
- 字号、圆角和阴影以语义令牌与既有组件变体表达。迁移前核对当前实际值，避免简单替换类名造成全局尺寸跳变。

这些是规范候选值，不是固定行数或平台性能门槛；需要结合中英文、用户字号设置和实际页面验收。

## 7 治理顺序

### 第一批 修复确定性问题

处理缺失工具类、彩色实心按钮对比、自定义焦点颜色，并核对全局 `small !important` 的具体影响。颜色与字号缺陷优先于页面重排。

验证使用真实 CSS 编译结果、颜色组合探针与对应控件截图，覆盖旧 WebView 兼容路径。不能仅以 typecheck 通过证明样式已修复。

### 第二批 收敛令牌与基础组合

明确颜色角色与过渡映射，建立控件、表面、字号和密度约定。清理共享组件对 Feature 类名的依赖，统一普通卡片与浮层的默认样式。

迁移已有调用方再移除兼容别名。保留必要的 Dockview、xterm、Markdown 和兼容性样式，不做全局字符串替换。

### 第三批 建立页面模板并迁移代表页

先以一个设置页和一个列表详情页验证容器、工具栏、滚动与移动端规则，再迁移同类页面。聊天与工作流编辑器按已确认的工作台方案单独处理。

建议优先选择决策模型／设置页验证表单模板，计划任务验证列表详情模板，然后处理 MCP、技能、插件和资源页。选择代表页是为了覆盖结构差异，不代表允许复制其业务规则到通用组件。

### 第四批 清理迁移残留

通过调用方核对与构建确认，移除不再使用的语义标记、跨页面祖先选择器、重复视觉组合和已无调用方的旧变量。保留明确的兼容需求和第三方适配。

不新增“文件行数超限”或“任意值出现次数”一类架构硬门槛。检查应验证具体契约，例如所用语义工具类能够生成、共享组件不依赖 Feature、前景背景组合可读、页面滚动与状态行为稳定。

## 8 验证矩阵

| 类别     | 必须检查的内容                                                     |
| -------- | ------------------------------------------------------------------ |
| 样式输出 | 语义工具类真实生成；动态变体可被扫描；无已失效类名                 |
| 颜色     | 浅深主题、预设与自定义色；文字、焦点、状态和选中效果               |
| 排版     | 字号设置、中英文长文案、`small` 与固定像素混用、代码字号独立性     |
| 布局     | 四种模板、侧栏展开／隐藏、窄屏、分屏、空态／错误／加载             |
| 滚动     | 页面、列表、详情、画布、终端各自的所有者；输入框与工具栏可达       |
| 可访问性 | 可见焦点、按钮与展开语义、触屏目标、减少动态效果                   |
| 兼容     | 保留 Safari 16 构建目标与产物检查，验证实际目标 WebView 的颜色降级 |

后续涉及多个前端区域时执行 `npm run check`；涉及主题映射、CSS 输出、入口或懒加载时执行 `npm run build`。再按影响范围运行 `npm run test:ui-ux`、`npm run test:chat-dock`、`npm run test:sidebar-projects`、`npm run test:mobile-shell` 等既有入口，并补充它们尚未覆盖的视觉状态。
