# 架构决策记录

改变长期依赖边界、公共协议、存储格式或平台架构的设计选择，应留下简短的架构决策记录。记录按需存入 `docs/architecture/<主题>.md`，不预建空目录；有关联专题文档时可以在原文维护决策并链接到代码。不要在多个位置复制同一决定。

文件数量不是是否需要独立记录的标准。遵循既定边界的局部移动、拆分或合并，只需在变更说明中填写下方结构变更记录；跨多个文件也不自动要求完整 ADR。结构治理可以独立成任务，无需附带新功能。

## 结构变更记录

- **问题与范围：** 当前职责混杂、错误归属或耦合的具体证据，以及本次治理的领域。
- **移动映射与公共接口：** 原路径到新路径、保留/移除的导出、受影响的调用方和客户端。
- **状态与依赖：** 谁拥有状态、持久化和生命周期，谁依赖谁；避免仅把原有共享 `this` 或整个 Runtime 对象搬到新文件。
- **验证：** 类型与行为测试、依赖检查、路由和懒加载、测试发现入口、源码守卫的变更及其替代保护。
- **迁移与回滚：** 存量调用方如何切换，是否影响协议/数据，如何按本次变更恢复；回滚不得覆盖既有用户修改。

拆分、保留共置和合并都需要以业务所有权、共同变化原因及接口成本解释。独立导出、没有共享状态或超过某个行数本身不构成拆分理由。一次结构变更应留下完整、可验证的调用链，不交付悬空导入或未接入执行入口的测试。

## 记录要求

每条记录应包含以下内容：

```markdown
# 标题

- 状态：提议 / 已采纳 / 已替代 / 已废弃
- 日期：YYYY-MM-DD
- 影响范围：前端、Runtime、TUI、桌面端、Android、iOS 或发布流程

## 背景

说明问题、约束和需要解决的长期风险。

## 决策

说明采用的方案和依赖方向。

## 替代方案

列出考虑过的方案以及没有采用的原因。

## 影响

说明兼容性、迁移成本、性能、测试和运维影响。

## 迁移与回滚

说明分阶段迁移、兼容期、回滚条件和清理旧实现的时机。

## 复查条件

说明什么变化会触发重新评估。
```

记录应链接到相关代码、协议测试、迁移脚本或发布说明，明确哪些内容已实现、哪些仍在迁移。源码守卫更新应说明原保护目标和替代验证，不能把“测试通过”单独作为架构合理的依据。状态发生变化时更新原记录；已知债务统一登记在 [`development-workflow.md`](development-workflow.md)，避免重复维护进度。
