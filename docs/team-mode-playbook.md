# Team Mode Playbook

> Pisper 团队模式（lead + subagent）的协作红线，来自一次真实 team 会话：5 项 UI 优化，lead 委派了 4 个 subagent（拆分重构 / 性能 / 无障碍 / UX）。本手册记录的每一次事故都真实发生过，代价包括单个卡死 agent 空耗 45+ 分钟、中断产生损坏工作区、以及中断后残留消息把工作流拖回未完成状态。

本手册仅在实际采用子代理时适用。用户要求独立完成或禁止子代理时，由主代理完成任务，不得为遵循本手册自行开启子代理。结构边界和守卫更新原则以根目录 `AGENTS.md` 为准。

## 背景：真实事故清单

| # | 事故 | 代价 | 对策章节 |
| --- | --- | --- | --- |
| 1 | 重构 agent 后期陷入反复全量验证循环，45+ 分钟无产出；lead 只能靠文件 mtime 判断是否卡死，最终中断接管 | 45+ 分钟空耗 | 升级与接管协议 |
| 2 | 中断恰好落在多文件重构中间，产生「主文件 import 已删除子文件」的损坏工作区；当时从 HEAD 恢复后重做 | 返工；若存在既有修改，还可能误覆盖 | 保存任务基线并按差异恢复的中断修复 SOP |
| 3 | 中断后此前发送的消息仍把工作流拉回未完成状态，阻塞目标完成，最后靠重新 spawn 收尾 | 额外等待与阻塞 | 升级与接管协议 |
| 4 | 各 agent 各自反复跑全量 `npm test` / `npm run build`，重复消耗大量时间 | 大量重复时间 | 验证分层策略 |
| 5 | 仓库有大量 `readFile + assert.match` 源码守卫测试，重构极易踩坏；必须在 spawn 消息里列明红线 | 回归风险 | 源码守卫测试红线 |

## 任务分解与文件所有权

- 分解任务前分别列出**写入白名单**与**只读上下文**。白名单覆盖所有拟新建、修改、移动和删除的文件；普通仓库上下文可以按需读取，不要求穷尽读取清单。凭据、用户数据和仓库外资源仍遵守安全边界。
- **写入范围重叠才构成所有权冲突。** 多个 subagent 可以读取同一上下文；不得并行写同一文件。需要改动共享文件时，由 lead 集成或串行交接，并通知仍在读取该文件的代理重新核验假设。
- 启动前由 lead 记录工作区基线，包括已有修改、未跟踪文件和文件所有者。必要时保存任务前差异与文件副本，不能把当前工作区一律视为 HEAD，也不能把其他人的未提交修改纳入回滚范围。
- 多文件拆分重构（例如把组件拆成主文件 + 多个子文件）必须作为一个整体任务交给单个 subagent。拆给多个 agent 后，任何一个中断点都可能留下「主文件 import 已删除、子文件未建好」的半成品状态。
- subagent 发现需要写入白名单之外的文件时，暂停该写入并向 lead 说明；可以继续不依赖该写入的只读分析。由 lead 扩充白名单并处理所有权后再修改，不要求用户处理常规内部协调。
- lead 维护全局写入所有权表，spawn 前检查冲突；只读任务的写入白名单为空。多文件结构变更的公共入口、调用方和测试调整必须有明确的集成人。

## 验证分层策略

验证按影响范围分两层执行；完整检查由 lead 集中运行，只有新修改、失败诊断或未解决疑点才重复。纯文档任务遵循开发流程中的文档检查，不机械执行全量测试：

| 层 | 执行者 | 允许的命令 | 说明 |
| --- | --- | --- | --- |
| 定向自验 | subagent | 分配任务所需的文本检查、类型检查或指定测试 | 只覆盖本任务；只读审阅不要求运行测试 |
| 集成闸门 | lead | 按影响范围选择 `npm run check`、`npm test`、`npm run build` 或平台检查 | 统一核验集成结果，记录实际执行和未执行的范围 |

定向测试示例（可一次传多个文件）：

```bash
npx tsx --test runtime/tests/agent-avatar-rendering.test.mjs
npx tsx --test runtime/tests/agent-avatar-rendering.test.mjs runtime/tests/api-handler-routing.test.mjs
```

- subagent 不运行 `npm test` / `npm run check` / `npm run build` 等全量检查，避免重复消耗和并发争用；发现需要扩大验证范围时交给 lead 集成验证。
- 禁止全量验证循环：**同一命令失败两次且无进展，立即停止并上报 lead**；不要第三次换参数重试，更不要「顺便」跑全量验证。
- lead 判断停滞时结合工具状态、检查输出、增量结论和 subagent 汇报；文件 mtime 只作辅助，只读审阅没有文件变更并不表示卡死。持续没有有效进展时进入升级与接管协议。

## 源码守卫测试红线

本仓库 `runtime/tests/*.test.mjs` 中有通过读取源码进行断言的测试，其中既有安全、依赖和兼容性约束，也有固定行数或具体代码形式的历史断言。守卫存在不意味着每一种写法都是永久架构约束；治理时需要保留原行为保护，并允许有依据地更新过时形式。

- 清点工具：`node scripts/list-source-guards.mjs` 可列出静态可解析的源码读取关系，不能枚举全部动态路径或解释每条断言。重构类任务附相关守卫文件、保护目标和已知冲突；再检索动态路径或间接读取，不能仅凭脚本未命中判断没有守卫。
- 执行重构的 subagent 将现有守卫视为**只读**，不得自行放宽或删除断言；新增行为测试按分配的写入白名单执行。
- 发现过时断言或必须改变被检查形式时，向 lead 提交原保护目标、冲突原因和替代验证建议，由 lead 负责更新并运行相关检查；subagent 不反复修改产品代码凑行数或匹配字符串。
- 完成标准是原行为、安全与兼容约束获得验证，依赖和职责边界清楚。需要更新的守卫与实现必须在同一集成变更闭合；尚未解决的失败如实报告，不宣称通过。

## 升级与接管协议

当 subagent 疑似卡死（长时间无文件变更、无汇报、或陷入验证循环）时，按顺序执行：

1. **发送收尾消息**：要求 subagent 在限定时间内交出当前状态——已改文件、未完成项、验证结果。
2. **等待一次**（约 30 秒）。
3. **核实状态**：结合工具状态、新增结论、检查输出和工作区差异判断；等待超时或 mtime 未变不能单独作为卡死依据。
4. **中断该 subagent。** 中断前就要有心理预期：**中断后工作区可能处于中间态**（import 已删但子文件未处理、文件写了一半等）。
5. **lead 接管**：确认旧任务及其后台进程已停止写入，按「中断修复 SOP」保全并修复工作区，再决定串行完成或重新分配。

两条附加红线：

- 中断之后，**不要再向旧 agent 发送任何消息**。真实教训：中断后此前发送的消息仍会把工作流拉回未完成状态、阻塞目标完成。收尾一律靠重新 spawn 新 subagent 或 lead 直接接管。
- 重新 spawn 的消息必须写明：这是接管收尾任务、当前工作区状态、已恢复的文件清单。

## 中断修复 SOP

中断卡死 subagent 后，lead 的标准修复流程：

1. **停止并保存现场**：确认旧任务及后台进程停止写入，记录状态，保存当前差异和未跟踪文件。保留任务前基线，不用 HEAD 替代基线。
2. **定位受损范围**：检查悬空导入、缺失导出、未完成移动和语法错误；按涉及语言运行适用的类型或语法检查。
3. **按归属修复**：比较任务前基线与当前差异，保留用户、其他任务和已完成的有效修改，只补齐或撤回本任务造成的损坏。禁止默认按整文件恢复到 HEAD；无法确定归属时保留现场，说明缺失信息，不猜测覆盖。
4. **闭合实现与守卫**：按原行为保护和已确定的结构边界完成迁移。确需更新守卫时，由 lead 记录替代验证；不要求逐字保留已经确认过时的形式。
5. **定向验证**：检查调用方、路由、公共入口、测试发现及相应行为，报告实际结果。
6. **集成交付**：由 lead 按影响范围补充检查并交付未解决项；恢复操作不得重写他人提交或误删既有修改。

## spawn 红线消息模板

每个 subagent 的 spawn 消息按此模板书写；重构类任务附相关守卫和保护目标。`⟨ ⟩` 内为占位说明，无对应条目时删除该行，但「写入白名单」「红线」「验证要求」「汇报格式」四节不可省略：

```text
【目标】
⟨一段话说明本任务要完成什么、验收标准是什么⟩

【写入白名单】（仅允许修改、新建、移动或删除下列文件；只读任务写“无”）
⟨- src/features/xxx/…⟩
⟨- runtime/tests/xxx-behavior.test.mjs（获准新增或修改的行为测试）⟩

【只读上下文】（推荐入口，可按需读取其他普通仓库上下文；不扩大写入权限）
⟨- runtime/tests/xxx.test.mjs（现有守卫：只读，可运行）⟩
⟨任务前工作区状态及需要保留的既有修改⟩

【红线】
- 现有源码守卫只读；冲突交给 lead，附原保护目标与替代验证建议。
- 不通过压缩代码、搬移共享 this 方法或凑字符串满足过时断言。
- 保留既有修改；不得默认整文件恢复到 HEAD，不得写入白名单外文件。
⟨重构类任务附相关守卫清单、保护目标和已知冲突；清单工具不覆盖全部动态读取⟩

【验证要求】
- 按任务范围执行：⟨文本检查、类型检查或 npx tsx --test runtime/tests/xxx.test.mjs⟩
- 不要运行 npm test / npm run check / npm run build；全量验证由 lead 在集成阶段执行。
- 同一命令失败两次且无进展，立即停止并上报 lead。

【汇报格式】
- 结论与改动文件清单（对照写入白名单；只读任务说明未修改）
- 执行过的验证命令及结果
- 未完成项与已知风险
- 发现的守卫冲突或名单外改动需求（如有）
```
